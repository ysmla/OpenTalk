# 图片隐私修复复核

日期：2026-10-14。基于提交 `2375c65`（修复实现 `18de3c6`）；开始核验时工作区干净。

## 结论

上一轮复核留下的未决问题已修复并转为常规回归测试；同一根因下的三处相邻缺口（编辑/删除、评论与回复目标、单个内容读取）也一并修复。祖先可见性现在由**一个**统一规则判定，图片隐私与内容可见性两轮验收均通过。

## 本轮修复：隐藏回答后，其下评论的图片仍可被游客读取

位置：`server/internal/content/attachments.go` 的 `attachmentReadableFor`。

### 根因

`active` 图片的可读性只把引用行与**根主题**对照。`JOIN contents root ON root.id=COALESCE(t.content_id,a.question_id,m.topic_id)`
把回答和评论一律回溯到根主题，于是"回答被隐藏"这个中间祖先从不参与判断：评论行与根问题都仍是 `visible`，图片继续对游客返回 200。

### 修复

祖先不再直接跳到根主题，而是逐级解析**直接祖先**，并要求该祖先自身可见：

- 主题：以自身为根（`t.content_id`）。
- 回答：直接祖先是所属问题（`a.question_id`）。
- 评论：直接祖先是所属回答（`m.answer_id`）、所在串的顶层评论（`m.parent_comment_id`），两者都没有时（主题下的直接评论）落到 `m.topic_id`。

三类祖先各用一个与引用行**互斥**的 `LEFT JOIN contents` 绑定（`pt`/`pa`/`pm`），任一祖先可见即放行。
"至少一条完整可见引用即可读"的规则保持不变，因此同一图片的隐藏引用不影响另一条公开引用。

过程中修正了两个实现层面的坑，都已写进代码注释：

1. 不能把祖先表与引用行 `JOIN` 到同一个 `contents` 别名——`c` 永远是引用行自己，`p.id` 不可能等于主题的 `content_id`，整个 `EXISTS` 会恒为假（本轮首次改动即因此让所有评论图片变成 404，已由测试捕获）。
2. 主题下的直接评论 `answer_id` 与 `parent_comment_id` 都是 NULL，其祖先只能由 `m.topic_id` 得到；漏掉这一支会使这类评论的图片全部 404。

`comments.parent_comment_id` 保存的是**串根**（`CreateComment` 在回复回复时也回填顶层评论），因此沿直接祖先判定已覆盖整条展示链，不需要递归 CTE。
（本轮后续又把这里从"沿直接祖先"升级为"走完整条链"，原因见下文"统一规则"一节：直接祖先可见推不出链的其余部分可见。）

### 回归测试

诊断用例已从 `reviewprobe` build tag 隔离改为常规测试，`server/internal/content/ancestor_review_test.go` 已删除。
`TestImagePrivacyBoundaries` 新增两个子测试，覆盖两类中间祖先：

- `隐藏回答后，其下评论的图片一并失效`：问题+回答+带图回答评论，游客先 200；隐藏回答后游客与另一登录用户都必须 404（评论行与根问题仍为 `visible`，只有中间祖先判断能拦住它）。
- `隐藏父评论后，回复里的图片失效而无关分支不受影响`：隐藏串根评论后回复图片 404，同时**无关的顶层评论图片仍为 200**，证明判定沿本条串而不是"一旦有隐藏就全拒"。

两个子测试都对修复前的代码失败（分别报 `got 200, want 404` 与 `got 404, want 200`），因此具备真实检出能力，不是恒真断言。

## 复核过程中另行发现的相邻问题（本轮已一并修复）

首轮复核时记录了三处同类祖先可见性缺口。它们与图片隐私同一个根因——可见性判定散落在各处、每处只按自己的需要取祖先。本轮已合并为一条规则并全部修掉。

### 统一规则

新增 `server/internal/content/visibility.go` 作为唯一判定入口：一段内容可达，当且仅当**它自身及祖先链上每一级**都未删除且未隐藏。每个读取路径改为调用它，不再各写一份谓词。

链是有限的（主题是自身祖先并终止；回答的祖先是问题；评论的祖先是所属回答、串根评论，两者都没有时是所在主题），因此一个朴素循环即可，不需要递归查询。循环带访问集合与深度上限，用于在数据违反 schema 时终止。

**规则被改为走完整条链，而不只是直接祖先**：直接祖先可见并不能推出链的其余部分可见（一条"隐藏问题→可见回答→评论"的链里，回答自身仍可见）。这个错误是本轮测试自己抓到的——首版实现只走一步，`隐藏根主题的行为保持不变` 子测试立刻失败。图片侧同样存在该问题，相应改为递归 CTE 展开整条链，并按引用逐条判定"该引用整条链都可见"。

### 修复的缺口

1. **隐藏回答后作者仍能编辑或删除该回答**（`edit.go`）：可编辑性原先检查目标行与根主题，跳过中间层。现在编辑与删除都走统一规则；删除额外保证隐藏回答不能用删除"脱身"。
2. **隐藏回答或隐藏串根评论后，仍能往其下新增评论或回复**（`comments.go`）：`answerBelongsToTopic` 与 `loadReplyTarget` 原先只检查目标行自身。现在两者都要求目标在当前可见链内，否则按 `INVALID_COMMENT_TARGET` 拒绝。
3. **隐藏根主题后，回答与评论的单个内容读取仍能成功**（`replies.go` / `comments.go` / `topics.go` / `edit.go` 的 `PublicContentByID`）：这些读取原先只检查目标行自身，而隐藏**不会**级联改写后代行（这与删除不同，删除有软删除级联）。因此隐藏问题后其回答、评论仍可按 ID 读出，违反 `requirements.md` 第117条与 `api/README.md` 第23条。现在这些读取统一返回 404。

图片侧（`attachments.go`）原有的"任一可见引用即可读"规则保持不变，并新增断言防止本轮改动收窄它。

### 新增回归测试

`server/internal/content/visibility_test.go`，5 个子测试：编辑/删除被拒且正文与 `deleted_at` 未被改动、回答下不能再发评论、串根评论不能再被回复、单个内容读取与图片一致拒绝、以及"隐藏根主题"这一较宽保证未被收窄。

**这些用例对修复前的行为全部失败**（实测：隐藏回答的编辑返回 200 而非 404、隐藏回答下新增评论返回 201 而非 422、串根评论被回复返回 201 而非 422、公开读取未返回找不到），因此具备真实检出能力。

### 一处未改的错误契约

`EditContent` 与 `DeleteContent` 先取根主题锁，而 `lockRootTopic` 对已删除/已隐藏的根返回 `ErrTopicNotFound`（`TOPIC_NOT_FOUND`），优先于统一规则的 `ErrContentNotFound`。也就是说，对"根主题被隐藏"这一种情况，编辑/删除返回 404 `TOPIC_NOT_FOUND`，而读取返回 404 `CONTENT_NOT_FOUND`。两者状态码一致、均不泄漏状态，差异只在错误码；现有测试（`delete_test.go`）依赖该错误码，故保留未动。
