# B2：本人内容列表与公开用户主页（2026-10-15）

## 结论

三个读取操作已实现，合同标为 implemented：`GET /api/v1/me/contents`、`GET /api/v1/users/{public_id}`（operationId `getPublicUser`）、`GET /api/v1/users/{public_id}/contents`。合同现为 **46 implemented / 11 planned（39 条已实现路径）**。

## 两个列表只差一件事，而那件事就是重点

| | `/me/contents` | `/users/{public_id}/contents` |
| --- | --- | --- |
| 本人匿名内容 | **包含**（是自己写的，隐去等于让历史不可用） | **排除** |
| 别人的匿名内容 | 不含（列表按 `author_id` 限定） | **排除** |
| 隐藏内容 | 不含（合同把作者引向通知查看处置结果） | 不含 |
| 已删除内容 | 不含 | 不含 |

排除匿名是在 **SQL 里**做的（`is_anonymous=FALSE`），不是在读取层过滤：读取器是共用的，日后有人改它也不该能让匿名内容冒出来。这是"可追溯匿名"与"可浏览匿名"的分界——匿名只经审计流程追溯，绝不靠翻某个人的主页。

`/me/contents` 里的匿名帖仍以**匿名模式**渲染（不会因为"是我自己"就换成昵称），有断言检查响应里出现 `"mode":"anonymous"`。

## 公开资料只给公开字段

`GET /users/{public_id}` 返回 `PublicUser`：`public_id`、`nickname`、可选 `avatar_url` 与 `bio`、`created_at`。测试逐个断言响应里**没有** `email`、`email_normalized`、`internal_user_id`、`role`、`account_status`。形态不可能存在或确实不存在的 public_id 都返回 404 `USER_NOT_FOUND`，不区分二者，避免帮助枚举。
