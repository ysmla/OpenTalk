# 回答与评论的作者操作入口（2026-10-15）

## 结论

详情页现在给**回答与评论**也提供了编辑/删除入口，作者可以管理自己的回答、评论与回复。同时在接入过程中发现并修复了一个**已有回复在刷新后不显示**的缺陷。

证据来自真实浏览器对真实 API 的走查（环境同 [内容侧前端浏览器走查](verification-2026-10-15-content-frontend-browser.md)），以及服务端权限端点返回值的逐一比对。

## 为什么不是逐条请求权限

接口对每条内容都提供 `GET /contents/{id}/permissions`，但一页有几十条回答与评论时，逐条请求会把一次阅读变成几十次调用。因此"这条是不是我的"改为**在客户端推导**（`web/src/lib/ownership.ts`），并且刻意只取**没有假阳性**的证据：

- 具名内容：作者的 `user.public_id` 与本人 `profile.public_id` 相同；
- 匿名内容：仅当作者显示为"楼主"**且**本人是该匿名主题的作者（权限响应里的 `force_anonymous_comment`）时才算自己的——"楼主"就是主题作者，两条事实合起来才成立；
- 匿名参与者的 `匿名#N` 内容**故意不认领**：判断哪个编号属于自己需要服务端，宁可少一个入口，也不能把编辑按钮放到别人的评论上。

编辑入口还要求距发布不超过 30 分钟（`EDIT_WINDOW_MS` 镜像服务端 `EditWindow`）且主题未被锁定。这里修了自己写的一个错误：起初用"是否禁止新增互动"（锁定**或**已解决）作为编辑条件，但服务端 `EditContent` 只拒绝**锁定**——已解决的问题仍可在时限内编辑。现在编辑看 `topic.is_locked`，新增互动才看"锁定或已解决"。

删除入口不受时限影响（与服务端一致：禁言取消发言但保留删除自己内容的权利），且删除前必须确认。

## 走查结果

| 场景 | 结果 |
| --- | --- |
| 作者查看自己的回答与评论 | 显示"编辑/删除"；问题虽已标记解决，编辑仍出现（与"已解决只禁止新增互动"一致） |
| 编辑时限边界 | 同一页面上 04:10 发布的回答与评论只显示"删除"，04:11 发布的回复仍显示"编辑"——与 30 分钟窗口一致 |
| 非作者查看他人内容 | 回答、评论与主题级操作**全部不出现**，没有假阳性 |
| 非作者查看他人的匿名"楼主"评论 | 只有"回复"，没有编辑/删除（安全关键方向） |
| 作者查看自己的具名评论 | 显示"回复/编辑/删除" |
| 删除回复 | 确认框"确定删除这条回复吗？删除后不可恢复。"，确认后该回复消失且提示"评论已删除。" |
| 与服务端一致 | 对同一条匿名评论，服务端给作者返回 `can_edit=true, can_delete=true, force_anonymous_comment=true`；给非作者返回 `can_edit=false`——与界面推导出的结果一致 |

## 顺带修复：已有回复刷新后不显示

`CommentsSection` 只请求了顶层评论（省略 `parent_comment_id`），所以**上一条回复在刷新页面后就消失了**，只有刚发布时因为进了本地状态才看得见。这是"评论只加载顶层第一页"这条已知缺口的实际后果，比"没有加载更多"更严重：读者会以为回复丢了。

现在加载时先取顶层评论，再对当前页的每个串根**并行**取一次回复（接口按设计一次只分页一层，见 `listComments` 的说明；一层一页才能保证两层展示分页一致）。代价是每条顶层评论一次请求，因此并发发出而不是串行。

修好后刷新页面即可看到既有回复，并且它自己的编辑/删除入口也随之可达。
