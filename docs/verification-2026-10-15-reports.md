# 举报内容（2026-10-15）

## 结论

`POST /api/v1/reports` 与 `GET /api/v1/me/reports` 已实现，合同标为 implemented（39 implemented / 18 planned，32 条已实现路径）。

**这是第 8 项的一半**：举报者这一侧。管理员队列（`GET /admin/reports`）、结案（`PATCH /admin/reports/{report_id}`）、可见性变更（`PATCH /admin/contents/{content_id}/visibility`，即隐藏/恢复）、管理审计与管理员删除他人内容**仍未实现**；举报目前会落库，但还没有供管理员处理的接口，也没有界面。

## 三条刻意的不变量

1. **举报不暴露举报者给内容作者。** 举报者只对本人与管理员可见；创建响应与本人列表都不含 `reporter_id` 之类会被作者读到的字段（有测试断言响应里没有该字段）。
2. **举报不改变被举报内容。** 它是主张而不是裁决：不隐藏、不锁定、不标记任何东西（有测试断言 `moderation_status` 仍是 `visible`）。这是"刷举报本身无法下架帖子"的实现层保证，也让审核决定保持可审计、这个端点没有任何副作用。
3. **不可见目标返回 404 而不是 403。** 否则举报就成了"这个隐藏 ID 是否存在"的探测器。隐藏、已删除、从未签发的 ID 三者行为一致。

## 唯一性：靠表，而不是靠先查后写

迁移里 `reports` 有生成列 `active_slot`（未结案为 1，结案为 NULL）与唯一键 `(reporter_id, content_id, active_slot)`，所以"同一用户对同一内容最多一个未结案举报"由数据库保证。实现直接 INSERT 并把 MySQL 1062 映射为 `ErrReportAlreadyActive` → 409 `REPORT_ALREADY_ACTIVE`：同一用户并发提交两次时，先查后写会双双通过检查再竞争，而唯一键无法被竞争绕过。结案后 `active_slot` 变 NULL，同一内容可以再次举报（有测试：结案 → 再举报成功 → 结案记录带着 `resolution_note` 与 `resolved_at`）。

## 输入边界

`content_id` 必须是正整数 ID；`reason` 必填、去空白后非空、≤500 字；`details` ≤2000 字（两者都先于数据库报错被拒）。`limit` 仍受 1..100 约束；游标绑定本列表（`my-reports`），别处的游标会被拒。

## 审核：隐藏/恢复与审计（2026-10-15 补做）

`PATCH /api/v1/admin/contents/{content_id}/visibility`（请求 `{visibility: visible|hidden, reason}`，响应 204）与 `GET /api/v1/admin/audit` 已实现。这是本仓库里**第一次**让"隐藏"可以不经数据库写入就发生——在此之前那条状态只能用 SQL 改，是本项目最痛的运维缺口。

**隐藏与删除是两个状态，刻意不混。** 隐藏只改 `moderation_status`：行、正文与标题都留在原处、不写 `deleted_content_archives`，所以可以恢复（有断言检查归档表仍为空）。已删除内容返回 404，因为它已被归档、没有可隐藏的正文。

**后代与附件不需要在这里遍历。** 可见性规则本来就同时读 `deleted_at` 与 `moderation_status`，所以隐藏一个主题之后，它的回答、回答下的回复以及其下所有附件都停止公开访问。测试断言了这条链：主题被隐藏后，**回答与评论的详情都返回 404、从搜索里消失、作者也无法再编辑它们或在其下新增回复**，而它们自己那几行仍是"未删除、未隐藏"。恢复只翻回一列，整棵子树随之回来。

**审计：一行 = 一次决定。** 重复同一个决定是幂等空操作且**不写审计行**（有断言：连续隐藏两次只留一行），因为审计记录只有在"这里确实做过一次决定"时才有用。写入与状态变更加在同一个事务里，并用 `SELECT … FOR UPDATE` 串行化，否则两个管理员同时操作会都读到旧状态、都写一行审计。审计载荷只有操作者、动作、原因与目标 ID，不含内容正文。

**权限**：只有 `role='admin'` 可以通过（`auth.Require(..., true, ...)`）；匿名 401、普通用户 403、管理员缺 CSRF 令牌同样 403——角色不能替代令牌。

## 未做（第 8 项的其余部分）

- **管理员举报队列（`GET /admin/reports`）与结案（`PATCH /admin/reports/{report_id}`）**：合同仍是 planned。举报能落库、能被举报者自己看到，但**管理员还没有接口去处理它**。这一块需要 `AdminReport` 的 `AdminUser`（reporter/handler）映射，是本项剩余的后端工作。
- 管理审计之外的其余管理操作：管理员删除他人内容、匿名追溯（`POST /admin/anonymous-traces`）、用户封禁（`/admin/restrictions`）、板块/标签管理、用户列表。
- **前端没有任何入口**：没有"举报"按钮、没有"我的举报"页、没有管理端界面（举报队列、隐藏/恢复按钮、审计列表）。所以目前举报与审核都只能用 curl 或后续前端接入——**这一项还不能算对用户完成**。
