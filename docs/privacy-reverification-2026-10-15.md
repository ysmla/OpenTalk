# 图片权限修复复核（2026-10-15）

基于 HEAD `2375c65` 加核验开始时工作区中的未提交修复（`internal/content/visibility.go` 及内容读写权限改动）。本轮**已修复**复核发现的两个边界问题，并把诊断用例转成常规回归测试；业务实现随之改动，详见下文"修复"一节。报告中的用例名与行号以 `2375c65` 加本次工作区改动为准。

## 结论

上轮"隐藏回答后，其评论图片仍公开"的用例已通过。本轮补充测试复现的两个边界问题（P1、P2）同属一个根因——**可见性判定在采样一条祖先，而不是走完整个祖先图**——现已一并修复。两个用例在修复前失败、修复后通过，均已转成常规测试。

## P1：回答下的回复跳过父评论权限（已修复）

位置：修复前 `server/internal/content/visibility.go` 的祖先表达式常量（当时只有 `COALESCE` 一种写法，第39行），以及 `attachments.go` 中重复的同一表达式。

### 根因

`COALESCE(...,cm.answer_id,cm.parent_comment_id,...)` 优先取回答 ID。回复同时带回答 ID 与串根评论 ID 时，权限遍历直接跳到回答，跳过串根评论。这不是"取错了一个祖先"，而是**该行有两个祖先、只检查了一个**：回答与串根评论彼此独立，隐藏任一个都必须让回复不可达。

### 复现（修复前）

创建公开问题、回答、回答下评论，再向该评论发布带图回复；只隐藏串根评论。游客读取回复图片返回 **200（预期 404）**，`contentVisible` 返回 **true（预期 false）**。

### 修复

祖先关系改为"**所有**直接祖先"，不再是一个值：

- `ancestorsExpression` 从 `COALESCE(...)` 改为 `CONCAT_WS(',',...)`，一次列出全部祖先：主题没有任何分支命中，得到空列表，遍历到此结束；回复列出回答与串根两条；
- 遍历从"跟随一个父节点"改为**按层展开的广度优先遍历**（`ancestorClosure`），并保留访问集合与深度上限；
- 一个内容可达，当且仅当**它所在闭包内的每一行**都未删除且未隐藏。闭包就是"该行及其全部祖先"，因此这与原规则等价，只是不再漏支。

## P2：隐藏一个引用的祖先会错误屏蔽另一个公开引用（已修复）

位置：`server/internal/content/attachments.go:190` 与 `:208`（修复前）。

### 根因

递归 CTE 只携带 `attachment_id` 与当前 `content_id`；`NOT EXISTS` 按 `attachment_id` 汇总，丢弃了每条引用链的起点。因此任一引用链存在隐藏祖先，就会否决同一图片的**所有**引用。

### 复现（修复前）

将同一图片用于回答下评论和另一个公开帖子；只隐藏回答。图片请求返回 **404（预期 200）**，尽管另一个帖子的引用链仍完全公开。

### 修复

图片侧不再自己实现一遍规则，而是**调用同一条规则**（`visibleContentIDs`）：先取出该图片的全部引用行，一次问"这些行各自是否可达"，再按"**任一可达引用即可读**"合并。

这一步同时消掉了 P1 在图片侧的同一个漏支：附件路径与内容读取路径现在共用 `visibility.go` 的祖先遍历，不可能再对"谁算祖先"给出两种答案。修复过程中曾尝试用 MySQL 递归 CTE 逐引用判定，但递归 CTE 的锚点成员被 MySQL 推断成不匹配的列数/类型（真实库上报 `ERROR 1222`、并把 `CONCAT_WS` 结果塞进 `parent_id`），且 CTE 无法表达"逐引用保留起点并求其闭包"以外的分支语义，故改为在 Go 里做同一张图的遍历——同一文件里已有 `contentVisible` 在做这件事，合并后规则只有一份。

## 修复中的两个自抓缺陷（记录以免重犯）

1. **工作切片别名**：广度优先的下一层切片最初复用了上一层的底层数组（`pending = pending[:0]`），把已收集的祖先 ID 覆盖掉，导致"答案自身的祖先集合"变成上一层的内容。表现为一个普通回答被判为不可见。已改为每层新建切片，并补注释说明原因。
2. **按行判定 ≠ 按链判定**：第一版 `visibleContentIDs` 返回的是"该行自身是否可见"，调用方直接取起点行，于是"起点可见但祖先隐藏"仍判为可达。这正是 P1 断言第二次失败的原因。现在函数返回的是"该行**整条闭包**是否可见"，语义与函数名一致，调用方不必也不该再做二次判断。

## 为什么这两个用例值得留下

两者都不是"边界上的手滑"，而是同一个设计缺陷在两条路径上的两次投影：**只要可见性判定允许"取一个祖先"，就一定会漏掉另一个**。所以留作常规回归测试的是**行为**（回复在串根被隐藏后不可达、另一条公开引用仍可读），而不是某一段 SQL——将来若有人再为图片侧写一个"更快"的谓词，这两个用例会立刻指出它又变成了采样。
