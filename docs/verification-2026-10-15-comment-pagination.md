# 评论分页与展开回复（2026-10-15）

## 结论

评论的两层都接上了各自的分页：顶层评论可以"加载更多评论"，每个串根的回复可以单独"加载更多回复"。此前顶层只加载第一页、回复没有分页（回复甚至只在刚发布时可见，见 [回答与评论的作者操作入口](verification-2026-10-15-answer-comment-actions.md)）。

## 为什么两层各自分页

接口按设计**一次只分页一层**：省略 `parent_comment_id` 返回顶层评论，某个串根的回复单独取。这不是实现偷懒，而是两层展示能保持一致的唯一做法——一页里混着两层，就可能出现"回复在这一页、它的串根在另一页"的半个线程。代价是顶层每条评论一次请求，因此对当前页的串根**并行**发出，而不是串行。

实现上顶层用现有的 `useCursorList`（累积游标列表，`加载更多` 追加、失败保留已加载项），回复挂在 `threads[rootId]` 上各自带 cursor 与 has_more。

## 走查结果

用真实 API 先造出超过一页的数据：主题 1 下 21 条顶层评论、其中第一条下 21 条回复（默认页大小 20）。

| 检查 | 结果 |
| --- | --- |
| 首屏 | 顶层 20 条 + "加载更多评论"；第一条串根 20 条回复 + "加载更多回复" |
| 加载更多评论 | 20 → 21 条，末条为"分页测试评论 21"，按钮消失（无下一页） |
| 加载更多回复 | 该串根 20 → 21 条，末条为"分页测试回复 21"，该串根的按钮消失，其他串根不受影响 |
| 新加载的顶层评论 | 同批并行取回其回复，不需要再点一次 |

## 走查过程中值得记下的一点

这一轮排查里，界面两次**看起来**没有渲染新按钮，而实际原因是 Vite 开发服务器在文件再次变动前一直给出**旧的模块转换结果**：页面上跑的是旧代码，`tsc` 与构建产物却是新的。判断依据是我在组件上加了一个临时属性探针，探针一出现按钮也同时出现——说明逻辑本身没问题。最终以"改文件 → 重新加载 → 再次读取 DOM"确认，探针已删除，没有留在提交里。

## 仍未做

- 评论**不能配图**（接口接受 `attachment_ids`，界面只给主题与回答接了上传器）。
- 标签 chip 未做成链接；列表不显示回答/评论数量（合同没有计数字段）。
- 未做并发与长列表性能测量：一页 20 条顶层评论会产生 20 次回复请求，串行改并行只是把延迟压到一个 RTT，请求数没变；如果以后一页评论很多，需要考虑服务端一次性返回整线程。
