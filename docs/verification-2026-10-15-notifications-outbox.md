# 站内通知与 outbox 写入（2026-10-15）

## 结论

内容提交时现在会在**同一个事务里**写站内通知与 outbox 事件，删除时立即作废尚未发出的投递。这一片落实了 `requirements` 的两条规矩：「自己的操作不通知自己；同一事件对同一接收者去重」与第 42 条「删除立即影响待发送通知，不能等清理任务」。本片不新增接口操作，因此没有改对外合同。

## 为什么写在这个事务里

SMTP 故障、worker 慢、两步之间崩溃，都**不能回滚**作者刚发布的回答或评论——需求写得很直白：投递失败绝不撤销发帖。所以事务只记录"发生了什么、谁该知道"，任何离开进程的动作（邮件）之后再读这条记录，并且在那个时刻**重新检查**可见性、身份展示与订阅设置，而不是信任此刻的判断。这正是 outbox 的意义。

两张表各司其职：

- `notifications` 是站内列表，每个接收者每个事件一行；
- `outbox_events` 是投递给投递层的持久交接，每个接收者每个事件一行。

两张表的事件键都是唯一索引，且键**只**由内容与接收者推导（`new_answer:<内容id>:u<接收者id>`），不含时间戳或计数器——这才使"重试的事务"是幂等的而不是产生第二条通知。有一条测试专门钉住这点：重新记录同一事件后，通知与 outbox 各仍只有一行。

## 通知谁：只通知被直接回应的那一层

| 动作 | 通知对象 |
| --- | --- |
| 回答问题 | 提问者 |
| 评论主题 | 主题作者 |
| 评论回答 | 该回答的作者 |
| 回复评论 | 被回复评论的作者 |

只通知直接目标是有意的：每一层在产生内容时已经通知过它的作者，若这里再往上通知整条链，一次回复会让同一个读者收到好几条消息，正好撞上"同一事件去重"的意图。作者的 id 只用于路由，永不出现在响应里；站内通知行**不存正文**，也没有作者字段——所以匿名身份的泄露面在数据结构上就不存在，摘要由读侧按同一条匿名规则附上。

## 删除时作废待发送投递

同一个事务里，对删除范围（含级联算出的全部后代）：

- `outbox_events` 中 `status='pending'` 的行直接删除——一条宣告"已经不存在的内容"的队列项没有话可说；
- `email_deliveries` 中 `status='pending'` 的行改为 `cancelled`；
- **已被 worker 租用（`processing`）的行不动**：取消一次在途发送是竞态，而 worker 会在发送前重新检查可见性并丢弃已经不可达的内容；
- **站内通知行保留**：那是接收者自己的历史，且正文从未被复制进去，读侧按当前可见性渲染即可。
