# B6b：管理端界面（账号与站点）（2026-10-15）

## 结论

B6 的第二片已完成：新增管理页 `#/admin/operations`「账号与站点」，覆盖 B3–B5 的全部管理能力。与 `#/admin/moderation`（举报队列、结案、内容隐藏/恢复、审计）分工明确：**一个处理队列，一个动手改东西**。

## 覆盖的能力

| 区块 | 操作 |
| --- | --- |
| 账号 | 用户列表（角色、是否封禁；**不含邮箱**）、提交禁言/封禁（可选截止时间，留空即永久）、处罚记录与撤销（撤销后标签变"已撤销"，记录保留） |
| 板块与标签 | 新建/按 ID 更新板块（名称、说明、类型）、新建/按 ID 更新标签；页面直接写出既有板块与标签的 ID 以便对照 |
| 主题处置 | 按内容 ID 锁定、置顶、移动到指定板块，原因必填 |
| 删除原文与匿名追溯 | 按内容 ID + 原因读取删除原文或追溯匿名作者；结果就地展示（原文用保留换行的等宽块，追溯显示作者、公开 ID、内部 ID、账号状态与**本次审计记录 ID**） |

## 界面里的两个刻意的表达

- **用输入框而不是下拉选择**：处罚与追溯以**内部用户 ID / 内容 ID** 为参数，而这两类 ID 本来就不出现在公开响应里，界面无法"列出候选"。与其做一个假的候选列表，不如让管理员填 ID，并把既有板块/标签的 ID 直接印在旁边。
- **不给"无原因"的路径**：服务端会把原因写进审计，所以界面在原因为空时直接禁用提交按钮——否则那条路径必然失败，只是把错误留给用户去撞。

匿名追溯的结果里同时显示**公开 ID 与内部 ID**，并标注账号状态：这正是"可追溯"的含义——追溯是管理员在留痕前提下的能力，不是公开信息。
