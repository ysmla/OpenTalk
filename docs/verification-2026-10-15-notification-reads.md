# 站内通知读取接口（2026-10-15）

## 结论

`GET /api/v1/me/notifications` 与 `PUT /api/v1/me/notifications/{notification_id}/read` 已实现，合同把这两个操作标为 implemented。这是内容包中唯一需要会话的读取，因此实现的三条设计都围绕同一件事：**通知不能变成绕过可见性与匿名的旁路**。

## 三条设计

1. **actor 在读取时附加，不在写入时固化。** 通知行只记录事件类型、接收者与内容 id；作者信息每次读取时从内容本身取，走与其它读取完全相同的匿名规则（匿名楼主显示"楼主"，其他匿名参与者显示"匿名#N"，匿名分支不带 `user` 对象）。
2. **内容不可见时整条不附作者。** 已删除或已隐藏内容的通知仍然列出（事件确实发生过），但 actor 被省略，摘要只说"该内容已被删除或不可见"，连事件类型都不点明；昵称、公开 ID、头像与匿名编号一并清空。有一条测试专门钉住这个方向：隐藏回答后，列表里既有该通知，又不含作者的任何标识。
3. **通知行不存正文。** 摘要只由事件类型推导，所以"先写通知、之后才隐藏或删除"这条路径上，正文不可能从列表里漏出来。

另外两条：站内通知**不随删除消失**（需求的删除条款约束的是"待发送"的通知，那是 6a 的范围，见 [站内通知与 outbox](verification-2026-10-15-notifications-outbox.md)）；标记已读**只允许接收者本人**，先读该行再更新——MySQL 对"值未改变"的 UPDATE 报 0 行受影响，否则"已读"与"不是你的"会无法区分，他人的或不存在的通知一律 404，不用于确认他人通知是否存在，重复标记幂等且不移动 `read_at`。游标按 id 倒序翻页且**不携带内部用户 ID**：游标是客户端可读的，内部 ID 没有理由出现在里面。
