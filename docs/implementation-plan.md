## 建议架构

- 单体 Go API + React Web，保持同源部署，减少会话和跨域复杂度。
- MySQL 为事实数据源，事务 outbox 保证内容提交后通知事件不会丢失。
- 独立 Go worker 进程处理邮件、重试、到期清理；可复用后端代码与二进制。
- Redis 处理短期验证码和限流，初期不主动加入内容缓存。
- 反向代理负责 HTTPS；图片放独立持久目录，经应用检查权限后提供。
- 本地和服务器使用可重复的配置与迁移流程；密钥通过环境配置注入，不进版本库。
- 这是架构建议，尚未锁定框架、依赖版本或服务器规格。

- 评论与回复已实现（2026-10-14）：`POST /comments` 覆盖三种形态——评论主题（`answer_id` 省略）、评论回答（`answer_id` 指定）、回复具体评论（`reply_to_comment_id` 指定）。回复同时写"线程根"与"被回复对象"：回复顶层评论时两者相同，回复回复时线程根保持不变，这正是界面两层展示所需。**跨目标回复必须由应用拦截**：`fk_comments_answer_topic` 是复合外键，而 `answer_id` 为 NULL 时外键不生效，所以"主题级评论去回复回答级评论"（及反向）数据库抓不到，只能在 `sameAnswer` 里比较可空性。回复目标与回答都必须属于同一主题且可见。评论同样过根锁，因此已解决问题对所有人生效；同样强制匿名并沿用讨论内编号。
- 解决状态切换已实现（2026-10-14）：`PATCH /questions/{topic_id}/resolution` 在**同一把根主题锁**内切换 open/solved——这是根锁存在的核心理由：拒绝新增互动的判断读的是 `resolution_status`，若不加锁，"标记已解决"与"新增回答"会各自读到旧状态并双双提交，留下一个本该被拒的新回答。只有提问者可切换，**管理员不例外**（是否解决是提问者的判断，不是审核动作）。切换**刻意不走** `guardNewInteraction`：锁定或已解决的问题必须仍能重新打开，否则 solved 会变成单向门、需求里的"重新打开"就无法满足。重复设置同一状态按幂等处理；solved 与 `resolved_at` 成对写入，open 清空（表上 CHECK 强制这一配对）。
- 内容编辑已实现（2026-10-14）：`PATCH /contents/{content_id}` 把三类权限**分开判定**——归属、30分钟时限、锁定主题禁止改正文。管理员不因角色获得捷径，因为这是授权而非审核动作。锁顺序仍是根主题优先：先无锁定位根主题ID，取其锁，再在锁内重新读取目标行并重新校验（若在此期间被删除则按404）。**时限从发布时刻计且不滑动**，编辑不会续期。`edited_at` 随正文一起写入。标题仅主题可改。附件清单**省略表示不改、空数组表示全部解除**，用指针类型区分二者；替换时先校验归属再整体重写。响应按内容类型分派 DiscussionTopic/QuestionTopic/Answer/Comment。
- 清理任务已实现（2026-10-14）：`cmd/admin -action cleanup` 清理过期待用附件、内容删除后的孤儿附件、以及到期归档的原文。**刻意不做成API进程内的定时器**——清理是低频运维动作，放进进程会让多实例各跑一遍、重启还打乱节奏；做成可重复执行的命令正好配合"失败可重试"的设计，代价是必须外部调度（development.md 给了计划任务示例）。每阶段先标 `pending_delete` 并提交、再删文件、只有文件确实删除才置 `deleted`，因此中断或失败的行下次会重来，**不会被提前标记为完成**；文件本就不存在按成功处理。孤儿附件只要还有未到期的删除归档引用它就会保留到归档之后（约30天），而不是7天——否则管理员复核原始材料时图片已经没了。

- 图片祖先可见性补齐（2026-10-14，复核二轮）：第一版祖先判定只回溯到**根主题**，漏掉中间祖先，因此隐藏回答后其下评论的图片仍对游客200。现在走完整条祖先链——主题是自身祖先并终止、回答取 `question_id`、评论取 `answer_id`／串根 `parent_comment_id`，两者都没有（主题下的直接评论）落到 `topic_id`；任一环不可见即不可读，"任一可见引用即可读"不变。两个新子测试分别钉住"隐藏回答→评论图片404"与"隐藏串根评论→回复图片404、无关评论仍200"。详见 [图片隐私修复复核](privacy-reverification-2026-10-14.md)。
- 可见性统一为一个入口（2026-10-14）：首轮复核记录的同类缺口已全部修复——**隐藏回答后作者仍能编辑/删除该回答**、**隐藏回答或串根评论后仍能往其下新增评论/回复**、**隐藏根主题后回答与评论的单个内容读取仍成功**。新增 `internal/content/visibility.go` 作为唯一判定入口，所有读取、编辑、删除、评论/回复目标与附件路径共用；`edit.go` 中重复的 `rootTopicOf` 已删除。关键教训写进代码注释：**隐藏不级联改写后代行，因此直接祖先可见推不出链的其余部分可见**（"隐藏问题→可见回答→评论"），必须走完整条链——这个错误是本轮测试自己抓到的。新增 `visibility_test.go` 5 个子测试，已实测对修复前行为全部失败。
- 祖先关系改为"全部祖先"且图片侧共用同一规则（2026-10-15，复核三轮）：两个新发现是同一个设计缺陷的两次投影——**只要判定允许"取一个祖先"，就一定会漏掉另一个**。其一，`COALESCE(...,answer_id,parent_comment_id,...)` 对同时带回答与串根的回复取到回答，隐藏串根后回复与图片仍可达；`ancestorsExpression` 改为 `CONCAT_WS` 列出全部祖先，遍历改为按层展开的广度优先（`ancestorClosure`，保留访问集合与深度上限），可达的判据改为"该行**所在闭包内每一行**都未删除未隐藏"。其二，图片侧的递归 CTE 只带 `attachment_id` 与当前行，`NOT EXISTS` 按 `attachment_id` 汇总，丢掉每条引用链的起点，于是一条引用的隐藏祖先否决了另一条公开引用；现在 `attachmentReadableFor` 不再自己写谓词，而是取出全部引用行后调用 `visibleContentIDs`，再按"任一可达引用即可读"合并。**教训**：本轮修复过程中自己踩到两个坑，已写进注释——广度优先的下一层切片不能复用上层底层数组（会覆盖已收集的祖先），以及"按行判定"不等于"按链判定"（起点可见但祖先隐藏仍须判不可达）。新增两个常规子测试，分别对两种旧实现失败。

   `GET /api/v1/search`：迁移 `000004_search_indexes` 加了两个 ngram 全文索引（`contents.body_md`、`topics.title`），`migrations.Latest` 升到 4。**关键点**：把两个 MATCH 写成 `OR` 等于没优化（实测 8.41ms，与 LIKE 扫描 11.4ms 相近，因为 OR 让两个索引都用不上），最终采用"两个索引子查询 UNION 后再 join"的形状（实测 **0.172ms**）。短于一个 ngram 词的查询（如单字）走原来的扫描回退，BOOLEAN MODE 运算符从用户输入里去掉后用引号包成短语。前端 `#/search?q=…&board_id=…&tag_id=…`，含板块/标签下拉（写入 hash，可从 hash 回填），混排结果带类型标签、回答与评论链接到所属主题，支持加载更多；已在真实浏览器验证。未做：中文语料质量与相关度排序、短词回退的索引化、全文索引写入代价的量化。
8. **举报与审核界面**（阶段 6）：隐藏/恢复目前只能由数据库写入；管理员删除他人内容也未实现（权限端点据此对管理员返回 `can_delete=false`）。
9. **阶段 7 上线准备**：部署脚本、TLS、备份恢复、SMTP 联调、端到端验收。`TRUST_PROXY` 必须保持 false 直到有反向代理覆盖 `X-Forwarded-For`。
