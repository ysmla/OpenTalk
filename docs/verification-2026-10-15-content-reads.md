# 内容读取端点实现与验证（2026-10-15）

## 结论

内容闭环的**读取侧**已实现：主题列表、单条内容（含删除占位）、当前会话权限、回答列表、评论列表、标签列表六个操作，合同状态由 planned 改为 implemented。全量测试在真实 MySQL 与独立临时 Redis 上通过。

本报告只覆盖读取端点与随附的合同/文档改动。**内容侧前端已在同一批次实现但尚未做浏览器级验证**，因此本报告不声称内容接口已通过浏览器验证。

## 为什么先做读取侧

统计合同后确认：内容闭环此前实现的是**写入侧**（发帖、回答、评论、编辑、删除、解决状态、图片上传），而列表与详情六个读取操作全部仍是 planned。前端没有可显示的数据源，所以读取侧是实现内容界面的前置条件，而不是可选项。

## 实现内容

| 操作 | 说明 |
| --- | --- |
| `GET /api/v1/topics` | 置顶恒在最前，其后按 `newest`（发布时间）或 `active`（最后活动时间）倒序；支持 `board_id`、`tag_id`、`resolution_status` 筛选；游标绑定排序与全部筛选条件 |
| `GET /api/v1/contents/{content_id}` | 按类型返回帖子/问题/回答/评论；隐藏内容统一 404；已删除内容返回不含原文、作者与图片的占位 |
| `GET /api/v1/contents/{content_id}/permissions` | 六项权限标志，未登录返回全 false 而非 401 |
| `GET /api/v1/questions/{topic_id}/answers` | 按发布时间正序；讨论帖 409，根问题不可见 404 |
| `GET /api/v1/topics/{topic_id}/comments` | 省略 `parent_comment_id` 返回顶层评论，填写则返回该串根的全部回复 |
| `GET /api/v1/tags` | 按名称排序、`q` 名称子串匹配，LIKE 通配符按字面转义 |

### 三条设计决定

1. **可见性不重写一遍。** 主题是自己的祖先，因此约束行即完整规则；回答与评论列表先由 SQL 缩小候选集，再把整页交给 `visibleContentIDs` 判定。SQL 只负责缩小范围，规则仍由 `visibility.go` 唯一实现决定——这正是本包被咬过两次的失败模式（采样一个祖先）。有一条 store 级测试专门钉住这一点：隐藏串根评论不会改写其回复行，所以 SQL 会把回复取出来，只有共享规则会拒绝它；删掉 `reachableComments` 该测试立刻失败。
2. **删除占位只在线路完整时出现。** 已删除行本身返回占位，但仅当其**祖先链全部可达**。级联删除后子内容仍按 404 处理：占位是用来描述"这条单独被删掉了"，不是用来确认一条已经整体消失的内容曾经存在。
3. **权限端点是写路径的镜像，不是发明。** 删除只有作者本人（管理员没有捷径，与当前 `DeleteContent` 一致）；编辑时限从发布时刻计且不滑动；禁言取消发言但不取消删除自己内容的权利；切换解决状态只属于提问者；匿名楼主被强制匿名。游客得到全 false。合同描述里明确写出"管理员删除他人内容尚未实现"，避免权限响应与 `DELETE` 的描述互相矛盾。

分页一律是 keyset：游标携带上一行的排序键，排序键由 SQL 自己投影（`DATE_FORMAT` 到整数）并随行返回，因此"游标来自哪一行"与"按什么排序"不可能各写一份而漂移。转成 epoch 会让排序依赖连接时区，而写入用的是 `UTC_TIMESTAMP(6)`，所以刻意避开。

## 顺带的重构（去重，不是改行为）

- `topicView`/`answerView`/`commentView` 的列清单与 join 各自成为唯一常量，单行读取与列表读取共用，列增删不会只改一边。
- `rootTopic` 的查询抽成常量：加锁读（`FOR UPDATE`）与只读各用同一段文本。
- `refuseMuted` 改收共享读接口（`queryer`），因此权限端点在事务外也能问同一个问题。
- 单内容详情、编辑、删除、图片路径继续共用 `PublicContentByID` 与可见性入口，没有新增第二套判定。

本轮第一次运行时 `read_test.go` 有 3 处失败，全部是**测试自身的问题而不是实现缺陷**，已修正并重跑全绿，记录在此以免被误读为"一次通过"：

1. 匿名身份断言用昵称 `author` 做子串检查，而 `author` 恰好是每个响应里作者对象的**字段名**，于是断言恒真。改为使用不会与字段名冲突的昵称，并同时断言 `public_id` 不出现。
2. 断言提问者不能回答自己的开放问题。**实现是对的**：没有任何规则禁止提问者自答，只有匿名提问者自答被强制匿名。断言已改为要求 `can_create_answer` 为 true。
3. 评论分页断言假设有两条可见顶层评论，当时实际只有一条，`has_more` 正确地为 false。已补第二条顶层评论并重写断言。

## 未验证项与风险（评审时请当作风险）

1. **没有浏览器级验证**：前端尚未在真实浏览器里对真实 API 走查，本报告不含该类证据。
2. **回答与评论数没有计数**：合同里没有计数字段，列表因此不显示"N 条回答/评论"。
3. **权限端点按内容逐条请求**：回答级编辑/删除按钮需要为每条回答单独取权限，前端当前只做了主题级入口。
4. **评论列表只加载顶层第一页**：前端尚未接入"某串根的全部回复"这个参数，展开更多回复的交互还没有。
5. **没有做并发与负载测量**：列表端点的查询次数已按页批量（标签与图片各一次），但未在大会话量下测量。
