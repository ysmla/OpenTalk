# 公开内容搜索（2026-10-15）

## 结论

`GET /api/v1/search` 已实现，合同标为 implemented。**这一项只做了后端与接口**：前端搜索界面尚未实现（见文末）。

## 两处刻意保守的设计（都写进了合同描述）

1. **匹配是子串，不是全文索引**：`LIKE '%q%'` 覆盖正文，并在有标题的行上额外匹配标题，因此帖子既能按标题也能按正文被找到。schema 没有全文索引，MySQL 的 ngram 解析器需要建索引才能用，所以这是诚实的第一版：正确、只搜可见内容、线性扫描。合同里"中文搜索策略仍需语料验证"说的就是这件事，没有把它说成已解决。
2. **排序按内容 id 倒序（最新在前）**：没有相关度信号可排，而稳定是 keyset 分页需要的性质。

`board_id` 与 `tag_id` 限定的是**内容所属的根主题**（`COALESCE(主题, 回答的问题, 评论的主题)`），因此回答与评论会随其主题被筛入或筛出——这与"搜索主题下的讨论"的直觉一致。

## 可见性不重写

SQL 只把候选缩小到未删除、未隐藏的行；然后整页交给共享的祖先规则判定；最后每一项都交给其它读取共用的 `PublicContentByID` 组装——它自己会再查一次。**这次重复检查是刻意的**：组装器是共用的，它不该信任调用方。若某一项在排序查询与这次读取之间变为不可见，它会被丢弃——搜索结果绝不能成为已移除内容还存在的地方。

## 输入边界

`q` 必填（空或纯空白 422）、不超过 100 字符（超长 422 而不是截断：长模式匹配不到有用的东西，只会让每一行更贵）；`LIKE` 通配符按字面转义（`%`、`_` 不会变成通配）；`limit` 仍受 1..100 约束；游标绑定筛选条件且不携带自由文本里的分隔符。

## 前端搜索界面（2026-10-15 补做）

- **路由**：`#/search?q=…`。检索词放在 hash 里，因此结果页可以链接、刷新与分享，不依赖我们的内存状态；`#/search`（无 q）显示空表单而不发请求。
- **界面**：搜索框（`maxLength=100`，空词不发请求——服务端也会拒绝）+ 结果列表 + 「加载更多结果」。主题页工具栏加了「搜索」入口。
- **混排结果**：接口一页里混着帖子、回答与评论，所以每条结果都带类型标签；只有帖子有自己的页面，回答与评论链接到它们所属的主题。删除占位只显示"已删除"和服务端给的文案，不显示原文也不显示作者。
- **匿名**：作者一律用共用的 `authorLabel` 渲染，因此匿名发帖在搜索结果里同样只显示匿名身份。

### 执行结果（真实浏览器 + 真实接口）

| 检查 | 结果 |
| --- | --- |
| `tsc --noEmit` / `vite build` | 通过（构建 106ms） |
| 接口（浏览器库真实数据） | `q=分页` → 20 条、`has_more=true`，前几条是评论；`q=zzznotfound` → 0 条 |
| `#/search?q=分页` | 标题「搜索」、搜索框预填「分页」、渲染 20 条结果、类型标签「评论」、链接指向 `#/topic/1`、有「加载更多结果」按钮 |
| `#/search?q=zzznotfound` | 0 条结果，显示「没有找到与「zzznotfound」匹配的可见内容。」，不显示加载更多 |

过程中发现并修掉一个环境问题：浏览器验证脚本启动的是**旧的** `browser-api.exe`（构建于搜索实现之前），因此首次请求 `/api/v1/search` 得到 404。重新构建该二进制后通过——这不是产品缺陷，但说明"跑一次冒烟"必须用当次构建的二进制，否则会得到误导性的 404。
