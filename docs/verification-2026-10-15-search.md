# 公开内容搜索（2026-10-15）

## 结论

`GET /api/v1/search` 已实现，合同标为 implemented。**这一项只做了后端与接口**：前端搜索界面尚未实现（见文末）。

## 两处刻意保守的设计（都写进了合同描述）

1. **匹配是子串，不是全文索引**：`LIKE '%q%'` 覆盖正文，并在有标题的行上额外匹配标题，因此帖子既能按标题也能按正文被找到。schema 没有全文索引，MySQL 的 ngram 解析器需要建索引才能用，所以这是诚实的第一版：正确、只搜可见内容、线性扫描。合同里"中文搜索策略仍需语料验证"说的就是这件事，没有把它说成已解决。
2. **排序按内容 id 倒序（最新在前）**：没有相关度信号可排，而稳定是 keyset 分页需要的性质。

`board_id` 与 `tag_id` 限定的是**内容所属的根主题**（`COALESCE(主题, 回答的问题, 评论的主题)`），因此回答与评论会随其主题被筛入或筛出——这与"搜索主题下的讨论"的直觉一致。

## 可见性不重写

SQL 只把候选缩小到未删除、未隐藏的行；然后整页交给共享的祖先规则判定；最后每一项都交给其它读取共用的 `PublicContentByID` 组装——它自己会再查一次。**这次重复检查是刻意的**：组装器是共用的，它不该信任调用方。若某一项在排序查询与这次读取之间变为不可见，它会被丢弃——搜索结果绝不能成为已移除内容还存在的地方。

## 输入边界

`q` 必填（空或纯空白 422）、不超过 100 字符（超长 422 而不是截断：长模式匹配不到有用的东西，只会让每一行更贵）；`LIKE` 通配符按字面转义（`%`、`_` 不会变成通配）；`limit` 仍受 1..100 约束；游标绑定筛选条件且不携带自由文本里的分隔符。

## 前端搜索界面（2026-10-15 补做）

- **路由**：`#/search?q=…`。检索词放在 hash 里，因此结果页可以链接、刷新与分享，不依赖我们的内存状态；`#/search`（无 q）显示空表单而不发请求。
- **界面**：搜索框（`maxLength=100`，空词不发请求——服务端也会拒绝）+ 结果列表 + 「加载更多结果」。主题页工具栏加了「搜索」入口。
- **混排结果**：接口一页里混着帖子、回答与评论，所以每条结果都带类型标签；只有帖子有自己的页面，回答与评论链接到它们所属的主题。删除占位只显示"已删除"和服务端给的文案，不显示原文也不显示作者。
- **匿名**：作者一律用共用的 `authorLabel` 渲染，因此匿名发帖在搜索结果里同样只显示匿名身份。

## 索引优化（2026-10-15 补做）

原实现对每一行做 `LIKE '%q%'`，B-tree 索引无法用于前导通配符，代价随论坛规模增长。迁移 `000004_search_indexes` 加了两个 ngram 全文索引（`contents.body_md`、`topics.title`；标题与正文分属两张表，所以必须两个索引）。`migrations.Latest` 随之升到 4，dev 库与浏览器验证库都已迁移。

### 关键发现：把两个 MATCH 写成 OR 等于没有优化

在 4000 主题 + 8000 内容、埋入已知关键词的临时库上用 `EXPLAIN ANALYZE` 实测三种写法：

| 写法 | 实际耗时（同一查询，21 条上限） |
| --- | --- |
| A) 旧的 `LIKE '%…%'` | **11.4 ms** |
| B) 两个 MATCH 用 `OR` 连在一个 WHERE 里 | **8.41 ms**（几乎没改善：OR 让两个全文索引都用不上，规划器仍走扫描） |
| C) 两个索引子查询 `UNION` 后再 join 回 `contents` | **0.172 ms** |

所以最终采用的是 C：候选集来自两个索引查找的并集，再与 `contents` 连接做筛选、可见性与 keyset 分页。这说明"加了索引"和"用上索引"是两件事——B 与 C 的差别不在索引，而在 SQL 形状。

### 随之而来的两个语义边界（都处理了，不是忽略）

- **短于一个 ngram 词的查询**（默认 2 字）：单字查询产生不出 token，全文索引无法回答。这类查询走原来的扫描路径，因此**单字搜索仍然正确**，只是代价是旧的（有测试与真机验证）。
- **BOOLEAN MODE 的运算符**：`+ - < > ( ) ~ * " @` 会被去掉，剩下的词用引号包成短语。否则 `-词` 会被读成"排除 词"，`*` 会被读成通配符——用户的字不该变成另一种查询。

## 结果页筛选控件（2026-10-15 补做）

板块与标签下拉框加在搜索表单里，选择写入 hash（`#/search?q=…&board_id=…&tag_id=…`），所以收窄后的结果页仍是一条可链接、可刷新、可分享的 URL；控件从 hash 回填，因此前进/后退与直接打开链接都正确。改筛选条件时沿用**已提交**的检索词而不是框里尚未提交的文字——否则会静默搜了别的东西。空结果提示在存在筛选条件时会说明这一点。

### 新测试抓到的两个真实缺陷

新写的短词/运算符测试当场抓到我自己实现里的两个 bug，都是"该用净化后的词却用了原始输入"：

1. 选择走索引还是走扫描时用了**原始**查询长度，于是 `-试`（2 字符、净化后 1 字符）被送去索引路径而匹配不到任何东西；
2. 回退路径的 `LIKE` 模式也用了**原始**查询（`%-试%`），同样匹配不到。

修完之后又暴露出第三个：只由运算符组成的查询被净化成空串后落进 `LIKE '%%'`，会**匹配全部内容**——空串检查因此移到分支之前。三处都是"看起来只是顺序问题、实际会返回错误结果"的错误。

## 未做
